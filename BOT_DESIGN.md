# Telegram-бот «Напоминания об оплате» — структура и дизайн

## 1. Цель

Бот следит за датами платежей из `payments.csv` и шлёт напоминания в Telegram.
Напоминание повторяется **каждые 2 часа** в течение дня, пока получатель не
нажмёт кнопку **«✅ Выполнено»**. Если платёж не подтверждён до конца дня,
напоминания продолжаются на следующий день по тому же расписанию (платёж
считается просроченным, но не «протухает»).

## 2. Получатели и роли

| Роль | Кто | Что видит |
|---|---|---|
| **Owner** | Влад | Напоминания **по всем** платежам (и своим, и Игоря) |
| **User** | Игорь | Напоминания только по **своим** платежам (`source == "Игорь"`) |

Соответствие `source → chat_id` в CSV отсутствует и хранится не в
`config.yaml` (он статический — только TZ и часы напоминаний, см. §6), а в
таблице `recipients` в `state.db` (см. §3.2) — так бот сам обновляет
соответствие через `/start`, не перезаписывая YAML-файл на диске.

Chat ID узнаётся через `/start`: бот сохраняет `update.effective_chat.id` в
`recipients` и просит владельца подтвердить, кто есть кто, — не нужно
доставать chat_id вручную через сторонних ботов.

**Правило рассылки для платежа `P` с `source = S`:**
- всегда отправить владельцу (Владу);
- если `S != "Влад"` — дополнительно отправить получателю `recipients[S]`
  (чтобы Влад не получал напоминание дважды за один и тот же платёж).

## 3. Данные

### 3.1 Источник — `payments.csv` (read-only для бота, правит человек)

```
id,date,source,amount
1,2026-08-04,Влад,5600
2,2026-08-08,Влад,4600
3,2026-08-08,Игорь,4600
...
```

Колонка `id` — стабильный идентификатор строки (число), чтобы состояние в
БД не «съезжало» при ручном редактировании CSV (сортировка, вставка строк
и т.п.). Новые платежи дописываются в конец с очередным `id`; существующие
строки не переставляются и не переиспользуют чужой `id`.

### 3.2 Состояние — `state.db` (SQLite)

Отдельная БД, куда при старте и по расписанию синхронизируется CSV.
CSV — источник истины по *данным платежа*, БД — источник истины по *статусу*.

```sql
CREATE TABLE payments (
    id          INTEGER PRIMARY KEY, -- из CSV
    date        TEXT NOT NULL,      -- YYYY-MM-DD
    source      TEXT NOT NULL,
    amount      INTEGER NOT NULL,
    status      TEXT NOT NULL DEFAULT 'pending', -- pending | done
    done_by     TEXT,               -- кто нажал кнопку
    done_at     TEXT,               -- timestamp
    created_at  TEXT NOT NULL
);

CREATE TABLE recipients (
    source      TEXT PRIMARY KEY,   -- 'Влад' | 'Игорь' (значение из payments.csv)
    chat_id     INTEGER NOT NULL,
    is_owner    INTEGER NOT NULL DEFAULT 0, -- 1 для Влада
    confirmed_at TEXT NOT NULL
);
```

Заполняется через `/start` (см. §5): первый, кто напишет боту и подтвердит
роль «владелец», становится Владом; остальные подтверждают своё `source`
из списка в CSV. Пока запись для `source` отсутствует в `recipients`,
напоминания по его платежам уходят только владельцу (см. §2).

**Синхронизация CSV → БД:** при старте бота и перед каждым тиком планировщика
бот перечитывает `payments.csv` (по mtime файла) и делает upsert новых строк
(`INSERT ... ON CONFLICT DO NOTHING`), не трогая уже существующие статусы.
Так можно дописывать новые платежи в CSV на лету, не боясь сбросить прогресс
по уже подтверждённым.

## 4. Расписание напоминаний

- Таймзона: `Europe/Moscow` (настраивается через env `TZ`).
- Основной ритм: **09:00, 11:00, 13:00, 15:00, 17:00, 19:00, 21:00** — cron-триггер
  APScheduler (`CronTrigger(hour="9,11,13,15,17,19,21")`).
- На каждом тике:
  1. sync CSV → DB;
  2. выбрать из БД все `payments` где `date <= today AND status = 'pending'`;
  3. для каждого — отправить (новое) сообщение-напоминание нужным получателям
     (см. §2) с инлайн-кнопкой.

**Немедленная первая отправка (не ждать следующего тика).** Как только платёж
становится «due & pending» (наступила его дата, а он ещё не подтверждён) и это
обнаружено *не в момент фиксированного тика* — например, при старте/рестарте
бота, либо сразу после синхронизации CSV, где обнаружен новый платёж с датой
`<= today` — бот шлёт напоминание **сразу**, не дожидаясь ближайшего 09/11/13/…
слота. Для этого в `payments` добавляется колонка `last_reminded_at`:

```sql
ALTER TABLE payments ADD COLUMN last_reminded_at TEXT;
```

Правило отправки (единое и для фикс-тиков, и для внепланового обнаружения):
`date <= today AND status = 'pending' AND (last_reminded_at IS NULL
OR now - last_reminded_at >= interval '2 hours')`. Это гарантирует, что даже
если сообщение ушло не по расписанию (сразу при обнаружении), следующее не
придёт раньше чем через 2 часа, а обычные фиксированные тики просто продолжат
подхватывать те платежи, что «созрели» к этому моменту.

Планировщик — **один периодический job** (плюс разовый прогон при старте
процесса) — а не job-на-каждый-платёж: это проще, переживает рестарт бота без
персистентного jobstore и не требует пересчёта расписания при правке CSV.

## 5. Telegram-интерфейс

### Сообщение-напоминание

```
💸 Напоминание об оплате
Дата: 08.08.2026 (просрочено на 2 дня)   ← если date < today
Кто платит: Игорь
Сумма: 4600

[ ✅ Выполнено ]
```

`callback_data = f"done:{payment_id}"`.

### Обработка нажатия кнопки

- `CallbackQueryHandler` ловит `done:<id>`;
- проверяет, что нажавший имеет право закрыть платёж (владелец — всегда,
  либо `source(payment) == текущий пользователь`);
- помечает `status='done', done_by=<user>, done_at=now()` в БД;
- редактирует нажатое сообщение → `✅ Оплачено 03.08.2026 в 14:32 (Игорь)`,
  убирает кнопку;
- если платёж закрыл не владелец — шлёт владельцу короткое уведомление
  «Игорь подтвердил оплату 4600 ₽ за 08.08.2026»;
- со следующего тика планировщика напоминания по этому `id` больше не шлются.

### Команды бота

| Команда | Действие |
|---|---|
| `/start` | Регистрация chat_id в `recipients` (см. §3.2), подтверждение роли, приветствие |
| `/pending` | Список неподтверждённых платежей (свои, либо все — для владельца) |
| `/list` | Ближайшие платежи на N дней вперёд — **доступно и Игорю**, но только по его собственным (`source == "Игорь"`); владельцу — все |
| `/help` | Справка |

## 6. Архитектура (модули)

```
reminder_bot/
├── config.yaml            # таймзона, часы напоминаний (chat_id — в state.db, см. §3.2)
├── payments.csv            # исходные данные (правится вручную)
├── state.db                 # SQLite, создаётся автоматически
├── telegram.key              # токен бота (НЕ коммитить)
├── bot/
│   ├── __init__.py
│   ├── config.py           # загрузка config.yaml + telegram.key
│   ├── storage.py           # CSV-парсинг, sync CSV→DB, CRUD по state.db
│   ├── scheduler.py        # APScheduler, cron-тик, рассылка напоминаний
│   ├── handlers.py          # /start, /pending, /list, callback "done:*"
│   └── main.py              # точка входа: init bot, storage, scheduler, run
├── requirements.txt         # python-telegram-bot, APScheduler, PyYAML
└── reminder-bot.service     # systemd unit для AWS EC2
```

Стек: **Python 3.11+, python-telegram-bot (async, v20+), APScheduler, SQLite
(stdlib `sqlite3`), PyYAML**.

## 7. Развёртывание на AWS EC2 (через git)

Уже готово:
- `ssh.command` — команда подключения (`ssh -i "osvc.pem" ubuntu@ec2-...`);
- `osvc.pem` — SSH-ключ (только для доступа с локальной машины, **на сервер
  не копируется**);
- `.venv` — локальное окружение (на сервере создаётся своё);
- репозиторий `https://github.com/PkQDark/osvc.git` — код бота деплоится
  через `git pull`, а не через `scp`.

**Важно:** репозиторий `PkQDark/osvc` — публичный. Данные в `payments.csv`
(даты, имена, суммы) не секретные — их можно коммитить и пуллить вместе с
кодом. А вот `telegram.key` (токен бота) и `osvc.pem` (SSH-ключ) — это
доступ к системам, они **никогда не попадают в git**, независимо от того,
секретны ли сами данные о платежах.

`.gitignore` уже настроен в репозитории (проверено):

```gitignore
osvc.pem
ssh.command
telegram.key
.idea/
```

К нему при реализации нужно будет добавить ещё `state.db`, `.venv/`,
`__pycache__/` — они появятся вместе с кодом бота.

`payments.csv` теперь версионируется в git: правки (новые платежи) вносятся
локально, коммитятся и пуллятся на сервер как обычный код — отдельного
`scp`-канала для данных больше не нужно.

### Первичная настройка

Локальный репозиторий уже создан и связан с
`git@github.com:PkQDark/osvc.git` (branch `main`) — этот шаг не повторяем.
Остаётся:

1. Разложить код по структуре из §6 (`bot/`, `requirements.txt`,
   `reminder-bot.service`), закоммитить и запушить (`git push`).
2. На сервере (через `ssh.command`) склонировать репозиторий и поднять venv:
   ```bash
   git clone git@github.com:PkQDark/osvc.git reminder_bot   # или https-вариант, если SSH-доступа к GitHub с сервера нет
   cd reminder_bot
   python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
   ```
3. Только `telegram.key` закинуть на сервер отдельно, **не через git**
   (SSH-ключ `osvc.pem` на сервер не копируется — он нужен только локально,
   для подключения):
   ```bash
   scp -i osvc.pem telegram.key \
       ubuntu@ec2-18-222-97-98.us-east-2.compute.amazonaws.com:~/reminder_bot/
   ```
   права: `chmod 600 telegram.key` на сервере.

### Обновление кода после первичного деплоя

```bash
# локально
git add . && git commit -m "..." && git push

# на сервере
ssh -i osvc.pem ubuntu@ec2-... "cd reminder_bot && git pull && sudo systemctl restart reminder-bot"
```

Обновление `payments.csv` (новые платежи) идёт **тем же git-пайплайном**:
правка локально → commit → push → на сервере `git pull` (можно тем же
скриптом, что рестартует сервис, — бот сам подхватит новые строки на
следующем тике за счёт CSV→DB синхронизации из §3.2).

4. systemd unit `reminder-bot.service` (коммитится в репозиторий как шаблон,
   на сервере кладётся в `/etc/systemd/system/`):

```ini
[Unit]
Description=Payment reminder Telegram bot
After=network.target

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/reminder_bot
ExecStart=/home/ubuntu/reminder_bot/.venv/bin/python -m bot.main
Restart=on-failure
Environment=TZ=Europe/Moscow

[Install]
WantedBy=multi-user.target
```

5. `sudo systemctl enable --now reminder-bot`.

## 8. Секреты и безопасность

- `telegram.key` и `osvc.pem` — доступ к системам (боту и серверу), они в
  `.gitignore` репозитория `PkQDark/osvc` **с самого первого коммита** (см. §7),
  несмотря на то что репозиторий публичный, а сами данные о платежах — нет.
  Проверять `git status` перед каждым `git add`, чтобы один из них случайно
  не попал в коммит.
- Если один из них всё же случайно закоммичен и запушен — недостаточно
  просто удалить его следующим коммитом (он останется в истории публичного
  репозитория): нужно сразу ротировать токен бота у @BotFather и/или
  пересоздать SSH-ключ в AWS.
- `payments.csv` — версионируется открыто, это осознанное решение (данные
  не секретные).
- Права на ключевые файлы: `chmod 600 osvc.pem telegram.key`.
- Токен бота читается из `telegram.key` в рантайме, не хардкодится в коде и
  не логируется.
- Проверка прав в `done:<id>` handler'е обязательна — иначе Игорь сможет
  закрывать чужие (Владовы) платежи.

## 9. Решённые вопросы

1. **chat_id** Влада и Игоря — получаются автоматически через `/start` при
   первом запуске бота каждым из них (см. §2), вручную доставать не нужно.
2. Игорь может смотреть свои платежи заранее — команда `/list` доступна ему,
   но фильтрует только `source == "Игорь"` (см. §5).
3. Первое напоминание не привязано жёстко к 09:00 — если платёж стал
   «due & pending» вне фиксированного тика (старт бота, синхронизация CSV),
   бот шлёт напоминание сразу, не дожидаясь ближайшего слота (см. §4,
   `last_reminded_at`).
4. Предварительная напоминалка (за день до даты) — **не нужна**, в MVP и в
   расширениях не закладывается.

## 10. Возможные расширения (не в MVP)

- Изменение/добавление платежей прямо из Telegram (только для владельца).
- Еженедельная сводка «сколько всего должно быть оплачено».
- Экспорт истории подтверждённых платежей обратно в CSV/Excel.
- Уведомление о новых просроченных платежах в отдельный «дайджест» раз в день,
  а не при каждом тике.
